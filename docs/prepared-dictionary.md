# Fixed-dictionary submission bundle

The dictionary is now confirmed to be fixed before submission. Dictionary
preparation can therefore run offline; every graded request still starts a new
Python process and pays for all runtime imports, data access, matching and stdout.

The compiler accepts dictionaries and matcher configuration only. It never reads
test addresses, expected results or predictions. The official dictionary can
replace test case 1 without changing the algorithm or build process.

## Build and run test case 1

Prepare the development inputs if they do not already exist:

```sh
python3.14 -m tools.prepare_dataset --source-dir testcases/1 --review testcases/1/review.json --output-dir reports/user-1
```

Compile the fixed dictionary:

```sh
python3.14 -m tools.compile_dictionary --dictionary reports/user-1/dictionary.json --output-dir reports/prepared-user-1
```

Then run the independent submission entry point, with one JSON string per stdin
line and one three-field JSON object per stdout line:

```sh
echo '"56/33 Nam Kỳ Khởi Nghĩa, Phường Bến Thành, Thành phố Hồ Chí Minh"' | python3.14 -S reports/prepared-user-1/submission.py
```

The entire generated directory is the bundle. Keep `submission.py`,
`matcher_runtime.py`, `dictionary.idx`, `manifest.json` and the generated
`__pycache__/matcher_runtime.cpython-314.pyc` together. Paths resolve beside
`submission.py`; the caller can use another working directory, and the repository
and original dictionary JSON are not needed at runtime. `--index PATH` explicitly
selects another prepared dictionary. Rebuild the bundle for the official data.

`-S` skips Python's site-package initialization. This application uses only the
standard library and does not need site packages. It is an explicit launch
configuration, not a subtraction from measured time. If the grader fixes the
launch command without `-S`, the corresponding default-startup timing applies.
See [CPython's startup documentation](https://github.com/python/cpython/blob/main/Doc/library/site.rst).

The checked-hash bytecode file is prepared before submission from the included
runtime source. Python validates it against that source. It is not generated by
an earlier graded request, and contains no dictionary-specific answers. If it is
omitted or unusable, Python can compile the included source, but that compilation
cost belongs to the cold request and is benchmarked separately below. Bytecode
is an optional acceleration with an explicit packaging dependency; it must be
accepted as part of the submission for its measured speedup to apply.

## How preparation removes the construction cost

`tools.compile_dictionary` builds the ordinary catalog and recovery indexes
offline, retaining their entry IDs, canonical labels, collisions and iteration
order. It writes normalized full/body lookups, province initials, possible window
lengths, compact/typing lookups, trigram frequencies/postings and target forms to
`dictionary.idx`.

The file has a power-of-two hash table whose slots point to individual records.
CRC32 selects a starting slot; complete key comparisons and linear probing
preserve correctness even for identical CRC32 hashes. The runtime opens a
read-only memory map and materializes only the entries and forms reached by
queries. Recovery reads cheap form metadata first; length-rejected forms do not
fetch full canonical entries. Form IDs are interned within the mapped store,
so repeated postings share one form without rebuilding full model hashes. It does not deserialize the entire dictionary or construct postings
for each process. Loaded records can be reused within a process; predictions
are never cached.

The standalone runtime is generated from the maintained matching source. The
compiler removes typing imports and annotations and emits small immutable model
constructors in place of runtime dataclass construction. It retains model
validation, equality/hash behavior needed by recovery, configuration replacement,
the normalization/retrieval/recovery/selection functions and diagnostic traces.
There is no separately maintained simplified matching algorithm. Unsupported
model declarations fail compilation rather than being silently approximated.

This path targets **CPython 3.14**. It uses CPython's `_json` string scanner and
string encoder for the narrow JSONL protocol, avoiding imports of a general
JSON document decoder on successful requests. Escapes, control characters,
surrogate handling and extra trailing documents have protocol regression tests.
Output strings remain correctly JSON-escaped. The ordinary package CLI continues
to use the general `json` module.

The data records contain primitive values in marshal format 4, with code objects
disabled on both write and read. The index checks its magic/version, structural
bounds, Python major/minor version, Unicode data version and generated-runtime
identity when opened by the bundle. Rebuild for a different runtime rather than
reusing an incompatible artifact. This replaces the earlier full-object pickle
experiment; there is no pickle loader in the submission path.

The manifest records dictionary identities, source identity, configuration,
file hashes and sizes, interpreter and build duration. Benchmark setup verifies
the complete bundle's hashes and confirms that the supplied evaluation dictionary
matches the compiled one. Full-file hashing is a build/preflight check, outside
request timing; individual file bounds and pairing checks remain inside it.

**The two bytecode + `-S` runs pass the requested launch-to-stdout interpretation locally. Normal startup and missing-bytecode means do not pass.** No startup or data-access time is subtracted.

If the grader waits for process completion, the endpoint changes the result:

| Configuration | Launch-to-exit mean ms | Observed exit max ms | Mean / max gates |
| --- | ---: | ---: | --- |
| Test case 1, prepared bytecode + `-S` | 10.811 | 21.599 | FAIL / PASS |

Consequently this is not evidence of compliance with a timer around `subprocess.run` that waits for child exit. The endpoint must match the actual grader.

Test case 1 has **515 dictionary labels** (162 streets, 319 wards, 34 provinces). Its prepared index is **604,366 bytes**. The scale fixture has **24,174 labels** (23,800 streets, 340 wards, 34 provinces); its counts and artifact sizes are retained in the manifest.

Both bytecode + `-S` runs cover **all 1,000 addresses in five rounds**, not a sample. All **5,000/5,000** cold outputs and all five 1,000-address batch rounds match the reviewed expectations for each dataset. The default-startup user run also has 5,000/5,000 correct outputs. Source-only timing uses **20 sampled addresses × five rounds**, all 100 outputs correct, plus five complete batches.

**163 unit tests pass**, compilation and whitespace checks pass, and complete diagnostic traces match the ordinary matcher on **1,000/1,000 user cases and 1,000/1,000 scale cases**, including candidates, scores and budget counts. Original user accuracy stays **994/1,000**.

The first scale probe averaged 10.228 ms on 20 sampled cases. Profiling identified eager entry loading for hundreds of length-rejected forms. After making form metadata and canonical-entry reads independent, the final scale run above covers all 1,000 cases and retains output/trace parity. This is a measured construction/access change, not removal of recovery features.

Machine-readable summaries, source/dataset identities, configurations, manifests, full-report hashes and coverage are in [prepared-dictionary-results.json](prepared-dictionary-results.json). Complete raw timings and predictions remain in the referenced reports under `reports/prepared-user-1/` and `reports/prepared-scale/`. All runs used CPython 3.14.4 on the local Linux machine.

The reviewed and original user expectations differ in six intrinsically
ambiguous accentless wards. Compilation preserves the existing null-on-ambiguity
policy; it does not encode either set of expected answers. These data are a
development set, not an independent accuracy holdout or the official dictionary.

The primary test-case-1 reports cover all 1,000 addresses in five seeded rounds:
**5,000 fresh interpreters and matchers per launch configuration**, zero cold
warmups. Each round also runs an independent shared-process batch as a throughput
diagnostic. Source-only coverage is explicitly sampled; the final supplementary scale run
also covers all cases in five rounds. Runs are sequential, without concurrent tests or profiling.

The parent timer starts immediately before process creation and stops when it
receives the complete stdout result line. It includes interpreter startup,
imports, index mapping/header checks, on-demand reads, matching, JSON parsing and
encoding, flushing and pipe transfer. There is no prediction file. Report writes,
fixture loading, bundle preflight verification and scoring are outside timing.
Every process must also exit successfully within its timeout; launch-to-exit is
recorded separately. Reader scheduling overhead is included. OS page caches are
uncontrolled, and preflight verification reads the bundle files.

A passing observed maximum is not a universal wall-clock bound. CPU speed,
runtime configuration, accepted launch flags, bytecode packaging, input lengths
and the official dictionary remain material to instructor compatibility. The
plain-Python launch and source-only results must not be represented as passing
when they miss the mean target.

## Reproduce the timings

Measure the recommended and default launch configurations separately:

```sh
python3.14 -m tools.benchmark_prepared --bundle reports/prepared-user-1 --dictionary reports/user-1/dictionary.json --cases reports/user-1/cases.jsonl --no-site --output reports/prepared-user-1/no-site-timing.json
python3.14 -m tools.benchmark_prepared --bundle reports/prepared-user-1 --dictionary reports/user-1/dictionary.json --cases reports/user-1/cases.jsonl --output reports/prepared-user-1/default-timing.json
python3.14 -m tools.benchmark_prepared --bundle reports/prepared-user-1 --dictionary reports/user-1/dictionary.json --cases reports/user-1/cases.jsonl --no-site --source-only --cold-cases 20 --output reports/prepared-user-1/source-only-timing.json
```

`--cold-cases 0` is the default and measures every address in every round;
`--cold-cases N` selects a seeded uniform sample without replacement.
`--source-only` copies only the source and index into an isolated directory and
uses `-B` so every request pays source compilation and no prior request can
create a bytecode cache for the next one. Failed children, malformed stdout and
timeouts abort the benchmark. A successful benchmark command produces a report;
its printed timing gates may still be FAIL.

## Validation

The prepared API and generated standalone runtime are compared against the
ordinary matcher at the complete trace level on the foundation, recovery and
typing fixtures. This covers candidates, scores, selected outputs, ambiguity,
budgets and exhaustion. Additional controls cover disabled features, generated
model immutability/validation, complete-key hash collisions, invalid headers and
runtime pairing, deterministic builds, JSON protocol failures, relocated bundles,
and execution without bytecode. The ordinary package API remains available.

The runtime-source and data artifacts are generated under ignored `reports/`;
the maintained compiler, loader, benchmark, tests and reviewed evidence are in
the repository. No test-case-1 source files or expectations are modified.
